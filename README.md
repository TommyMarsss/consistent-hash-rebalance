# 热点感知的一致性哈希分片系统

纯 Go 标准库实现的一致性哈希分片系统：带虚拟节点的一致性哈希环 + 访问热点检测 + 动态拆分迁移，并保证迁移过渡期内任意 key 的路由唯一确定。附自动化测试与单文件静态 HTML 可视化报告（原生 HTML/CSS/JS，无任何第三方库）。

## 运行

```bash
go test ./...          # 运行全部自动化测试
go run ./cmd/sim -out report.html   # 运行模拟并生成 HTML 报告
open report.html       # 在浏览器中查看可视化报告
```

## 一、一致性哈希环设计（`ring.go`）

- **哈希空间**:`[0, 2^32)` 的环。`HashKey` 使用 FNV-1a（`hash/fnv`，标准库）后再经一次 32 位 bit-mixing 终态混合（MurmurHash3 的 fmix32 公开算法，直接以位移/乘法实现，非第三方库）。
  - 为什么需要终态混合：FNV-1a 对 `node-1#vnode-37` 这类短小、高度相似的字符串分散性很差，实测 150 虚拟节点时节点负载占比在 0.09~0.24 之间剧烈偏移；加混合后落在 0.157~0.184，迁移比例才能贴近理论值 1/N。
- **虚拟节点**：每个物理节点贡献 `vnodesPerNode`（默认 100~150）个环上点，点位置 = `HashKey(node + "#vnode-" + i)`。虚拟节点平滑了负载分布，也让单点增删只影响相邻弧。
- **弧（分片）归属约定**：点 `i` 拥有弧 `[points[i].hash, points[i+1].hash)`；key 由"最后一个 hash ≤ hash(key) 的点"服务（前驱约定，越界回绕到最后一个点）。查找用二分（`sort.Search`)，O(log V)。
- **最小化迁移**：加节点时，只有被新点"切走"的弧段的 key 迁移，且全部迁往新节点，理论比例 = 新节点占比 ≈ 1/(N+1)；删节点时只有原本落在被删节点弧上的 key 迁移，理论比例 ≈ 1/N。测试（`ring_test.go`）在 5 万 key 上验证：实测 0.1726 / 0.1675 vs 理论 0.1667，且**断言了没有任何无关 key 被重新分配**（加节点时所有移动的 key 必须落到新节点；删节点时只有原在被删节点上的 key 才允许移动）。

## 二、热点检测与动态拆分（`hotspot.go`、`manager.go`）

- **统计窗口**：按 epoch 统计每个分片的访问次数（`Manager.RecordAccess` / `WindowStats`)。
- **热点判定**（双条件，缺一不可）:
  1. `hits > Factor × 全环平均分片访问量`（默认 `Factor = 3.0`)—— 相对条件，只抓真正的离群分片；
  2. `hits ≥ MinHits`（默认 200)—— 绝对下限，避免系统整体安静时小噪声触发拆分。
  - 阈值选择依据：Factor=3 对 Zipf 式偏斜流量足够敏感又不会因均匀流量的泊松涨落误触发（均匀流量下单分片超过 3 倍均值的概率极低）;MinHits 过滤冷启动期的低基数抖动。两者均可通过 `HotspotDetector` 配置。
- **拆分策略**：热点分片（一段连续哈希弧）被等宽切成 2~3 段（超过 2 倍热点阈值时切 3 段），第一段留在原节点，其余各段分别迁往**当前窗口负载最低的其他节点**，让多个节点分担热点，而不是简单整体搬家。
- **防抖动**：拆分后该分片进入 `Cooldown` 个 epoch 的冷却期；与进行中迁移重叠的分片不会再次拆分；并发迁移数有上限。
- **无重叠无遗漏**：拆分点按等宽划分 `[lo, hi)`，保留段 `[lo, p1)` + 迁移段 `[p1, p2) ... [pk, hi)` 恰好拼接成原区间。`hotspot_test.go` 对此有显式断言（相邻段首尾相接、无重叠、末端恰好等于原区间终点）。

## 三、迁移过渡期的路由一致性（`shard.go`、`manager.go`）

迁移不是瞬时完成的，过渡期路由规则必须保证**任意时刻任意 key 有且仅有一个服务节点**。实现方式：

- 每个进行中的迁移记录 `{LoU, HiU, From, To, CursorU}`：区间 `[LoU, HiU)` 正在从 `From` 迁往 `To`,`CursorU` 是单调前进的游标。
- **路由规则**(`Manager.RouteHash`)：先查活跃迁移表——若 key 落在某个迁移区间内，则 `hash < CursorU`（已拷贝）路由到 `To`，否则路由到 `From`；不在任何迁移区间的 key 走哈希环。由于各迁移区间互不重叠（拆分前会检查重叠），任意 key 至多命中一条迁移记录，路由结果唯一确定。
- **游标只前进不后退**，因此一个 key 的所有权至多翻转一次（`From → To`)，不存在来回振荡的窗口。
- **原子提交**：迁移完成后才把新拆分点插入哈希环（`InsertPoint`)，此后该区间直接由环路由到新节点；提交前后路由结果一致（游标已到区间末端，迁移表规则与环规则给出相同答案）。
- 测试（`migration_test.go`）在迁移推进的每一步对全部 3 万 key 断言：区间内 key 严格按游标规则路由到 `From`/`To` 之一、区间外 key 路由不变、重复查询结果一致；另有并发迁移互不干扰的测试。模拟器每个 epoch 抽样 4000 key 做同样的不变量校验，报告中 `consistencyErrors` 恒为 0。

## 四、可视化报告（`report.go` → `report.html`)

`go run ./cmd/sim` 运行一段 28 epoch 的模拟（4 节点起步，epoch 4~14 注入热点流量，epoch 18 加节点，epoch 24 删节点），生成**单一静态 HTML 文件**：数据以 JSON 内嵌，全部渲染逻辑为原生 SVG/Canvas/JS，不启动服务、不引入任何框架。内容包括：

- 哈希环上各分片（弧）按节点着色的分布图；
- 外环 256 桶访问热度叠加 + 底部热力图柱状图，可用时间轴（滑块/播放）逐 epoch 回放；
- 触发再平衡的分片高亮（黄色弧）与迁移路径（指向目标节点的箭头）;
- 事件日志（拆分开始/完成、节点增删）与节点增删迁移比例校验表（实测 vs 理论 1/N，以及"是否仅涉及增删节点")。

## 五、测试覆盖

| 测试 | 覆盖需求 |
|---|---|
| `TestAddNodeMigrationRatio` / `TestRemoveNodeMigrationRatio` | 节点增删迁移比例 ≈ 1/N，且仅涉及增删节点的 key |
| `TestRingArcsCoverFullHashSpace` / `TestRoutingDeterministic` | 环弧恰好铺满哈希空间、路由确定性 |
| `TestHotspotDetectionThreshold` | 热点阈值（倍数 + 绝对下限）的触发时机 |
| `TestSplitTriggeredAndKeySpaceIntegrity` | 无热点不拆分、有热点才拆分；拆分后 key 空间无重叠无遗漏 |
| `TestRoutingConsistencyDuringMigration` | 迁移过渡期每一步的路由唯一性、游标规则、区间外 key 不受影响、提交后归属正确 |
| `TestConcurrentMigrationsDisjoint` | 并发迁移区间不相交、每个 key 至多被一条迁移认领 |
| `TestSimulationInvariants` | 端到端：热点必触发拆分、迁移全部完成、一致性错误为 0、增删比例符合预期 |

## 目录结构

```
ring.go        一致性哈希环（虚拟节点、二分查找、弧/分片视图）
shard.go       分片区间、迁移游标、区间重叠判定
hotspot.go     热点检测器（倍数阈值 + 绝对下限）
manager.go     路由管理器：热点拆分、迁移推进与提交
sim.go         模拟器：请求流、热点注入、节点增删、不变量校验
report.go      单文件静态 HTML 报告生成（内嵌数据与原生 JS）
cmd/sim/       命令行入口
*_test.go      上述全部测试
```
